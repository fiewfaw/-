# Care Navigator Lead Registry And LINE Handoff Design

**Date:** 2026-08-11
**Status:** Approved conversation design, pending written-spec review
**Applies to:** Seven public Team 4 result pages, the existing `#packages` service section, Google Sheets, and the future LINE OA chatbot

## Objective

Create a separate, consent-based Lead Registry for people who generate a personalized Team 4 plan. The registry gives each pending lead an opaque reference code that works in two ways:

1. Any external AI can read and discuss the human-readable Care Navigator plan while ignoring the opaque reference code.
2. The official Baan Kaiyaphap chatbot can recognize the reference code, privately resolve the saved contact and plan, confirm the details with the user, and hand a qualified lead to the owner.

The existing anonymous Google Sheets marketing-event system remains unchanged. It continues to receive only allowlisted anonymous funnel events and must never receive Lead Registry data.

## Product Flow

```text
Team 4 personalized plan generated
        |
        | explicit temporary-storage consent
        v
Lead gateway creates pending lead + opaque lead code
        |
        +--> Copy for AI
        |      - readable assessment and plan
        |      - opaque lead code
        |      - no name, phone, or precise location
        |
        +--> Consult physiotherapist
               - existing service/pricing page remains visually unchanged
               - lead handoff context is retained in the browser
               - LINE OA opens with a short prefilled lead-code message
               - the user presses Send once
                         |
                         v
               Official chatbot resolves code privately
                         |
                         v
               masked confirmation + contact consent
                         |
                         v
               qualified lead for owner callback
```

Copy for AI is optional and is not a required handoff step. Closing the Team 4 page before copying must not destroy the pending plan or prevent the service-page-to-LINE route.

## System Boundaries

### 1. Anonymous Marketing Events - existing and unchanged

The current owner-only marketing workbook and Apps Script receiver continue to accept only:

- `discovery_entry`
- `authority_asset_viewed`
- `app_started`
- `team4_viewed`
- `personal_plan_created`
- `ai_summary_copied`

This system must continue rejecting names, phone numbers, contact details, locations, assessment answers, scores, plan text, and chat messages.

### 2. Lead Registry - new and separate

Use a different private Google Spreadsheet and a different server boundary. Do not add lead columns, tabs, or lookup behavior to the anonymous event workbook.

The public Team 4 page never reads Google Sheets directly. It sends a strict payload to the Lead Gateway on the existing VPS. The gateway validates and writes the Lead Registry through owner credentials. Only the official chatbot and owner workflow may resolve lead codes.

### 3. Clinical Core - excluded

The Lead Registry is a contact and pre-service handoff system, not a clinical record. It does not write to the separate Clinical Core. A converted lead can enter the Clinical Core only through a later, explicitly approved owner workflow.

## Lead Data Contract

### Public create request

The Team 4 client may submit only the following fields after the user accepts the temporary-storage notice:

| Field | Rule |
|---|---|
| `schema_version` | Exact integer `1` |
| `request_id` | Browser-generated UUID for idempotency |
| `contact_name` | Trimmed Thai/Latin text, 1-80 characters |
| `phone` | Exactly 10 Thai mobile/telephone digits after normalization |
| `service_area` | Optional coarse area text, maximum 120 characters |
| `plan_type` | One of the seven approved Team 4 plan IDs |
| `plan_summary` | Final AI-ready summary, maximum 12 KB UTF-8 |
| `consent_version` | Exact approved consent copy version |
| `consented_at` | ISO timestamp generated by the browser and bounded by server time |
| `app_version` | Controlled Care Navigator version |

The public create request must not include raw Team 1-3 answer history, precise coordinates, Google Maps URLs, national IDs, email, free-form chat, attachments, or arbitrary metadata.

### Server-generated values

| Field | Purpose |
|---|---|
| `lead_id` | Internal random identifier |
| `lead_code` | Human-copyable opaque code such as `CN-X7K9P2M4` |
| `resume_token_hash` | Hash of a separate browser recovery secret |
| `created_at` | Authoritative server time |
| `expires_at` | Pending-lead expiry time |
| `status` | `pending`, `confirmed`, `contacted`, `converted`, `closed`, or `expired` |
| `confirmed_at` | Chatbot confirmation time |
| `contacted_at` | Owner contact time |
| `source` | Coarse approved discovery source only |

The lead code and resume token are different secrets. The lead code alone cannot retrieve a lead through a public endpoint. The browser receives the lead code plus a one-time recovery token; only a hash of the recovery token is stored.

## Google Sheets Layout

Create a new owner-only spreadsheet named `Care Navigator - Pending Leads` with these tabs:

### Leads

One current row per lead with explicit columns only:

`lead_id`, `lead_code`, `created_at`, `expires_at`, `status`, `contact_name`, `phone`, `service_area`, `plan_type`, `plan_summary`, `consent_version`, `consented_at`, `app_version`, `source`, `confirmed_at`, `contacted_at`

### Status History

Append-only state changes:

`change_id`, `lead_id`, `changed_at`, `from_status`, `to_status`, `actor_type`, `reason_code`

Do not write raw chat text to this tab.

### Lookup Audit

Append-only official lookup outcomes:

`lookup_id`, `lead_id`, `looked_up_at`, `actor_type`, `result_code`

Allowed result codes are `found`, `expired`, `already_confirmed`, `not_found`, and `invalid_code`. Do not store the submitted message or full code for failed lookups.

### Data Dictionary

Human-readable meaning, allowed format, sensitivity, and retention for every column.

The spreadsheet remains private to the owner account. It is not shared by link and is not readable by public browser clients.

## Lead Code And Recovery

- Generate at least 80 bits of cryptographically random lead-code entropy.
- Use an uppercase, transcription-safe alphabet that excludes ambiguous characters such as `0/O` and `1/I`.
- Do not use sequential numbers, phone fragments, dates of birth, plan scores, or names.
- Store only the opaque `lead_code` in Copy for AI.
- Store `lead_code` and the separate recovery token in browser storage on the same origin.
- Store no name, phone, precise location, raw answers, or plan text in browser storage.
- The recovery token authorizes retrieval of only the matching AI-ready plan and lead code until expiry. It never returns the saved phone or contact name to public JavaScript.
- If browser storage is cleared or the user changes device, the old plan cannot be publicly recovered. The user may create a new plan or continue through the chatbot's manual-contact fallback.

## Copy For AI Contract

All seven Team 4 pages must use one shared envelope while preserving each plan's current clinical summary:

```text
=== CARE NAVIGATOR PLAN V1 ===
Reference code: CN-X7K9P2M4

Instructions for AI:
- Analyze and answer from the Care Navigator plan below.
- Do not diagnose, replace a clinician, or remove safety warnings.
- The reference code is only for the official Baan Kaiyaphap chatbot.
- Ignore the reference code when providing clinical or exercise analysis.

[Existing plan-specific assessment, FITT, warnings, and article links]
=== END CARE NAVIGATOR PLAN ===
```

The copied text contains no contact name, phone, precise location, or recovery token. An external AI can use the complete plan content but cannot resolve the reference code.

## Service Page And LINE Handoff

The existing service and pricing page remains visually and editorially unchanged.

When a user reaches it from a Team 4 consultation button, the browser retains the active lead handoff context without placing contact details or plan text in the URL. When the existing LINE contact action is used with an active, unexpired lead, it opens the official account chat using LINE's HTTPS URL scheme with this short prefilled message:

```text
ต้องการปรึกษาจากแผน Care Navigator
รหัสอ้างอิง: CN-X7K9P2M4
```

The user presses Send once in LINE. If there is no active lead context, the existing LINE action behaves normally and opens the official account without a lead message.

## Official Chatbot Contract

The LINE webhook runs on the VPS, verifies the untouched LINE request body and official webhook signature, and then parses messages.

When a valid lead code is present:

1. Resolve it through a server-only Lead Registry interface.
2. Reject invalid, expired, or purged codes without disclosing whether a phone number exists.
3. Reply with masked confirmation only, for example `คุณส***` and `******1234`.
4. Show the plan title and ask whether the details are correct and whether the user wants a callback.
5. On explicit confirmation, bind the current LINE user to the lead internally, mark the lead `confirmed`, append status history, and notify the owner workflow.
6. On correction, ask only for the incorrect contact field and record the correction as a new audited state change.
7. On refusal, close the handoff without notifying the owner for a callback.

The chatbot never sends the full saved contact or plan into a group chat. Emergency wording in the saved plan remains visible and cannot be replaced by a sales response.

## Consent And Retention

Before Team 4 sends the create request, display compact copy next to the existing create-plan action:

> ระบบจะเก็บข้อมูลติดต่อและสรุปแผนนี้ไว้ชั่วคราว 14 วัน เพื่อให้คุณส่งแผนเข้ามาปรึกษาโดยไม่ต้องกรอกใหม่ หากไม่ส่งกลับมา ข้อมูลส่วนบุคคลจะถูกลบอัตโนมัติ

Pressing the create-plan action after this notice records consent version and time. The user can still use the general, non-personalized plan without submitting contact data.

Retention rules:

- `pending`: purge contact and plan after 14 days; keep only anonymous aggregate counts.
- `confirmed` or `contacted`: keep up to 90 days for lead follow-up.
- `converted`: transfer only through an approved owner workflow, then remove contact and plan from the Lead Registry within 30 days.
- `closed`: purge contact and plan within 30 days.
- Audit rows retain status codes and timestamps without contact or plan text.

An automated daily expiry job enforces these rules. Manual deletion by lead code is available to the owner.

## Failure Handling

- Lead gateway unavailable: still generate and display the personalized plan locally; explain that the consultation reference could not be saved and allow retry. Anonymous analytics remain non-blocking.
- Duplicate `request_id`: return the original lead code and expiry without adding a second row.
- Invalid contact or oversized summary: reject without partial storage and keep the form available for correction.
- Clipboard denied: show the existing copy failure message; consultation through the service page remains available.
- Expired lead in LINE: explain that the saved reference has expired, then offer a new Care Navigator link or manual contact capture.
- Missing browser recovery token: do not expose a public lookup by lead code; use the manual fallback.
- Google Sheets or VPS outage: do not claim that the lead was saved or that the owner will call back.

## Security Controls

- HTTPS only.
- Exact production-origin allowlist plus explicit localhost development origins.
- Strict content type, body-size cap, closed schema, and forbidden-field checks.
- Per-origin and coarse abuse rate limits without writing IP addresses into Google Sheets.
- Server-side Google credentials only; no Sheet ID credentials or lookup secret in public JavaScript.
- Constant-shape lookup responses for invalid and unavailable codes.
- Idempotent create and confirm operations.
- LINE webhook signature verification before JSON parsing or business logic.
- No contact or health payloads in URLs, analytics events, application logs, error messages, or browser telemetry.
- Logs use request IDs and result codes only.

## Review And Testing

### Contract tests

- Accept all seven approved plan IDs and reject unknown IDs.
- Normalize and require exactly 10 phone digits.
- Reject unknown fields, precise coordinates, Maps URLs, attachments, and oversized summaries.
- Create idempotently by `request_id`.
- Lead codes are random, non-sequential, and collision checked.
- Public recovery requires the matching recovery token and never returns contact fields.
- Official lookup requires server authentication and records an audit outcome.

### Browser tests

- Every Team 4 personalized-plan action creates one pending lead only after consent.
- Copy for AI contains the shared envelope and lead code but no contact fields.
- Existing plan-specific clinical content remains present.
- Closing and reopening on the same browser restores the latest unexpired plan reference.
- The consultation action still reaches the existing `#packages` service section.
- The existing LINE action receives a prefilled lead-code message only when an active lead exists.
- The app still produces a usable plan when the Lead Gateway is unavailable.

### Chatbot tests

- Valid, invalid, expired, duplicate, corrected, and refused lead flows.
- Masked confirmation never exposes another person's full contact.
- Replayed LINE webhooks do not duplicate status changes or owner notifications.
- Messages without a lead code continue through the normal FAQ and Care Navigator routing.
- Emergency content receives the safety response before sales handling.

### Release gate

- Use synthetic leads only until create, recovery, expiry, deletion, LINE signature verification, masked confirmation, and owner notification pass end to end.
- Verify the anonymous marketing workbook still rejects all Lead Registry fields.
- Verify the new Lead Spreadsheet is private and distinct from the marketing workbook.
- Do not publish the Lead Gateway URL or enable real contact storage before backup, deletion, and incident-disable procedures are tested.

## Acceptance Criteria

- Anonymous events and identifiable leads remain in separate workbooks and server interfaces.
- Every personalized Team 4 plan can produce one opaque lead code without changing the approved plan design.
- Copy for AI works with external AI and contains no contact data.
- Official LINE chatbot can privately resolve the same lead code, confirm masked contact details, and hand off a qualified lead.
- A user who closes the Team 4 page before copying can continue from the same browser or send the lead code through the service-page LINE action.
- The user always presses Send once in LINE before the chatbot processes the lead.
- Pending leads expire and personal data is purged automatically.
- Lead-system failure never blocks access to the personalized plan.
