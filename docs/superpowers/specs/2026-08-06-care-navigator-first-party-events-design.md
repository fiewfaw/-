# Care Navigator First-party Event Collection Design

**Date:** 2026-08-06  
**Status:** Approved architecture, pending written-spec review  
**Supabase target:** Existing empty project in `fiewfaw@gmail.com's Org`  
**Excluded project:** `baan-physio-clinical-core`

## Objective

Collect anonymous, first-party journey events from the Baan Kaiyaphap website and Care Navigator so the business can learn which discovery sources and authority assets lead to meaningful app use. The collector must never become a clinical record, must not receive health answers or contact details, and must never block the user from receiving a plan.

## Scope

### Public browser events in MVP

The public collector accepts only these six event names:

1. `discovery_entry`
2. `authority_asset_viewed`
3. `app_started`
4. `team4_viewed`
5. `personal_plan_created`
6. `ai_summary_copied`

The remaining funnel events (`summary_returned_to_bot`, callback, booking, patient start, and retention) are not writable by a public browser. They will be added later through trusted LINE OA, Facebook, and owner workflows.

### Explicitly excluded

- Names, phone numbers, email addresses, and precise locations
- Diagnoses, symptoms, assessment answers, scores, and plan text
- Raw chat messages and attachments
- Full URLs or query strings
- IP addresses or raw user-agent strings stored in the event table
- Reads from the event table by anonymous or authenticated public clients
- Any schema, function, or data change in `baan-physio-clinical-core`

## Architecture

```text
Website / Care Navigator
        |
        | strict anonymous event payload
        v
Supabase Edge Function: collect-marketing-events
        |
        | validate, normalize, rate-limit, insert
        v
public.marketing_events (RLS enabled, no public policies)
        |
        +--> internal aggregate views / Codex review

baan-physio-clinical-core remains separate and untouched
```

The static website cannot host an API. A Supabase Edge Function therefore acts as the only public write boundary. The browser never receives a database secret and never writes the table directly. The function uses a server-side secret to insert validated rows.

## Components

### 1. Browser event client

A shared browser script is used by the website, Next.js static export, and the seven Team 4 HTML pages.

Responsibilities:

- Create a random session ID in `sessionStorage`; it ends with the browser session.
- Derive discovery source from an explicit UTM allowlist or coarse referrer category.
- Accept only event names and dimensions declared in the marketing registry.
- Queue at most 50 anonymous events in `sessionStorage` when delivery fails.
- Batch at most 10 events per request and retry with bounded backoff.
- Use `fetch` with `keepalive` where supported.
- Never throw into the user journey or block navigation, plan generation, or copy actions.
- Provide an opt-out flag and respect browser privacy settings where available.

No persistent cross-session identifier is introduced in MVP. Cross-visit attribution can be considered later only with a clear privacy notice and an approved consent design.

### 2. Edge Function `collect-marketing-events`

The function is a public HTTP endpoint because visitors do not log in. JWT verification is disabled only for this function; its body implements the application boundary.

Controls:

- Accept `POST` and `OPTIONS` only.
- Allow CORS only for `https://baankaiyaphap-chonburi.com` and approved localhost origins.
- Require `application/json` and reject bodies above 16 KB.
- Accept 1-10 events per request.
- Validate with a strict schema; unknown fields are rejected rather than silently stored.
- Reject forbidden keys such as name, phone, email, diagnosis, answers, plan, message, URL, coordinates, and location.
- Enforce enum allowlists and conservative string length limits.
- Use the server receive time as the authoritative timestamp.
- Insert idempotently by client-generated `event_id`.
- Apply a coarse per-session hourly cap without storing the caller IP.
- Return only accepted/rejected counts and never echo the payload.
- Avoid logging request bodies.

Origin checks and session limits reduce accidental and casual abuse but are not treated as strong authentication. Anomaly monitoring and idempotency are required because any public analytics endpoint can receive synthetic traffic.

### 3. Database table

`public.marketing_events` uses explicit columns instead of a free-form JSON payload.

| Column | Purpose |
|---|---|
| `event_id uuid primary key` | Idempotency key generated by the browser |
| `received_at timestamptz` | Authoritative server timestamp |
| `occurred_at timestamptz` | Client event time, accepted only within a bounded range |
| `event_name text` | One of the six public event names |
| `anonymous_session_id uuid` | Session-only journey correlation |
| `discovery_source text` | Approved source enum |
| `asset_type text` | Approved authority asset enum |
| `asset_id text` | Controlled article/content slug |
| `entry_variant text` | Approved landing or entry variant |
| `campaign_id text` | Optional campaign code |
| `creative_id text` | Optional creative code |
| `app_version text` | Deployed Care Navigator version |
| `schema_version smallint` | Event contract version |

Database controls:

- Enable RLS immediately.
- Create no `anon` or `authenticated` read/write policy.
- Revoke table privileges from public roles.
- Add check constraints for event/source/asset enums and string lengths.
- Add indexes for date, event name, discovery source, and asset reporting.
- Keep the table out of Realtime publication.
- Use a limited retention period for raw events; retain aggregate counts longer.

### 4. Internal review layer

MVP review is performed through Codex against owner-only database views rather than exposing another dashboard publicly.

Initial views:

- Daily event counts
- Funnel by discovery source
- Authority asset to app-start performance
- Care Navigator completion funnel
- Duplicate/rejected-event monitoring

The views contain aggregate counts only. They do not expose individual sessions to public clients.

## Event Payload

```json
{
  "schema_version": 1,
  "events": [
    {
      "event_id": "uuid",
      "event_name": "app_started",
      "anonymous_session_id": "uuid",
      "occurred_at": "ISO-8601 timestamp",
      "discovery_source": "google_organic",
      "asset_type": "knowledge_article",
      "asset_id": "frailty-in-older-adults",
      "entry_variant": "care_navigator_home",
      "campaign_id": null,
      "creative_id": null,
      "app_version": "beta-1"
    }
  ]
}
```

Fields not relevant to an event remain `null`; no arbitrary metadata object is accepted.

## Data Flow

1. A visitor opens the website or Care Navigator.
2. The browser creates a session-only random ID.
3. The page records an allowlisted event locally.
4. The client batches and posts the event to the Edge Function.
5. The function validates origin, body size, event name, dimensions, and forbidden keys.
6. Valid rows are inserted idempotently; invalid rows are rejected and counted.
7. The function returns success without returning stored data.
8. Codex queries aggregate views when the owner requests a marketing review.

## Failure Handling

- Network or Supabase outage: queue within the current session and retry later.
- Queue full: discard oldest event; never affect app operation.
- Invalid payload: reject with `400`; do not partially store an invalid row.
- Disallowed origin: reject with `403`.
- Rate cap exceeded: return `429` with a retry hint.
- Duplicate event ID: treat as already accepted.
- Database failure: return `503`; client keeps a bounded retry queue.
- Free-project pause or cold start: app remains fully usable; events may retry during the session.

## Instrumentation Points

- Website entry: `discovery_entry`
- Article, video, About, service, credential, case, review, or app asset: `authority_asset_viewed`
- First Team 1 selection: `app_started`
- Team 4 result successfully shown: `team4_viewed`
- Personalized plan successfully generated: `personal_plan_created`
- Copy-for-AI action succeeds: `ai_summary_copied`

Each event must fire once per meaningful action. Page re-rendering must not create duplicate events.

## Testing

### Local automated tests

- Client allowlist and forbidden-field tests
- Session ID and queue bounds
- Source classification and UTM normalization
- Event deduplication
- Edge Function method, origin, size, schema, and forbidden-key tests
- Database constraint and RLS tests
- Instrumentation tests for each Care Navigator action
- Static checks that all seven Team 4 pages load the shared event client

### Supabase verification

- Apply schema to the approved empty marketing project only.
- Verify anonymous and authenticated roles cannot select or insert directly.
- Invoke the Edge Function with a valid event and confirm one row.
- Replay the same event ID and confirm no duplicate row.
- Send forbidden fields and confirm no row is written.
- Send from a disallowed origin and confirm rejection.
- Run Supabase security and performance advisors after schema deployment.

### Product verification

- Complete the live journey from website entry through Copy for AI.
- Confirm six expected events appear in order with one session ID.
- Confirm the app still completes when the collector endpoint is unavailable.
- Confirm no contact or health data appears in the table, function logs, URLs, or browser queue.

## Rollout

1. Build and test the schema, function, and client locally.
2. Apply the schema and deploy the function to the approved empty Supabase project.
3. Verify database security before adding the public endpoint to the app.
4. Instrument Care Navigator and Team 4 pages behind an environment-controlled collector URL.
5. Publish the static app through the existing narrow deployment workflow.
6. Run one synthetic end-to-end journey and review stored rows.
7. Start collecting real anonymous events.
8. Add trusted LINE OA and owner-only conversion events in a separate later phase.

## Acceptance Criteria

- The approved marketing Supabase project receives the six anonymous public events.
- `baan-physio-clinical-core` has no schema, function, or data change.
- Public clients cannot read or directly write the event table.
- Forbidden contact and health fields are rejected before insertion.
- Care Navigator remains fully functional during collector failure.
- Duplicate delivery does not duplicate rows.
- Owner-only aggregate queries answer discovery, authority, and Care Navigator funnel questions.
- Automated tests and the production static build pass before publication.
